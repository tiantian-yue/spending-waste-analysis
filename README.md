# 大学生闲置消费识别与预警系统

山西财经大学信息管理与信息系统专业本科毕业设计（作品设计类）。
《大数据技术与应用》课程大作业与毕业设计共用本代码库。

## 题目

**大学生闲置消费识别与预警系统设计与实现**

题目 19 个汉字，符合学校"一般不宜超过 20 个汉字"的要求。
原拟题目《基于个人消费账单的大学生闲置消费识别与预警系统的设计与实现》共 29 汉字，超限 9 字，已压缩；
"基于个人消费账单"这一层信息下沉到说明书的数据来源章节。

核心问题：只用账单里已有的字段（时间、金额、品类、交易对方），能不能在一笔消费发生前，
判断出它有较大概率会变成闲置？

数据来源为本人微信 / 支付宝账单（官方"用于个人对账"通道自行导出），
并在系统内逐条标注"闲置 / 在用"，标注结果构成模型训练标签。

## 本地启动

```bash
# 1. 复制环境变量模板
cp .env.example .env
# 2. 按本机情况修改 .env 里的 DB_PASSWORD
# 3. 建库（首次或需要重置时执行）
mysql -uroot < sql/01_schema.sql
mysql -uroot < sql/02_seed.sql
# 4. 导入账单（把导出的账单放进 data/，先空跑确认解析无误）
python scripts/import_bills.py --dry-run
python scripts/import_bills.py
# 5. 拼多多品类回填（依赖 data/pdd_orders_raw.csv，见下文）
mysql -uroot < sql/03_backfill_pdd.sql
# 6. 商品名补全（本地专属：需要你自己的拼多多订单导出，产物不入库）
mysql -uroot < sql/04_add_goods_detail.sql
python scripts/gen_goods_detail_sql.py --csv data/pdd_match.csv data/pdd_match_all.csv
mysql -uroot < sql/05_goods_detail.sql
# 7. 食品改判（本地专属：靠上一步的商品名，把零食生鲜移出标注范围）
python scripts/reclass_food_as_groc.py --write-sql
mysql -uroot < sql/06_food_as_groc.sql
# 8. 服务改判（本地专属：驾校/话费这类服务不存在「买回来闲置」）
python scripts/reclass_service.py --write-sql
mysql -uroot < sql/07_service_out.sql
# 9. 生成三个页面（研究用工作台 / 产品用体检页 / 结果回传页），并跑自检
python scripts/gen_label_workbench.py
python scripts/gen_waste_checkup.py
python scripts/gen_result_import.py
node scripts/selftest_workbench.js "闲置盘点工作台.html"
node scripts/selftest_checkup.js   "浪费体检.html"
# 10. 启动
python run.py
```

启动后访问 http://127.0.0.1:5000/health ，返回 `{"status": "ok"}` 表示环境正常。

### 拼多多品类回填（2026-10-14）

账单里拼多多的扣款只写「先用后付」，**716 笔交易在账单层面完全没有商品信息**
（微信/支付宝的账单没有商品字段，这不是解析问题，是数据源问题）。

解决路径：拼多多订单列表页不显示订单号也不显示时间，但**商品标题、店铺、实付
金额都在**。用抓取脚本导出页面原文（`拼多多订单导出助手.html`，失败时自动落
兜底原文），再由 `scripts/parse_pdd_orders.py` 离线解析还原出 1695 条商品行，
`classify_pdd_goods.py` 按关键词归类，`match_pdd_to_bills.py` 以
**金额 + 先用后付标签 + 顺序对齐** 三重判定匹配回交易：

| 判定 | 笔数 | 占比 |
|------|------|------|
| 唯一（该金额只对应一件商品） | 368 | 51.4% |
| 同类（多候选但大类一致） | 102 | 14.2% |
| 顺序对齐（候选数 = 交易数，按位置对齐） | 207 | 28.9% |
| 跨类（取主导类，待人工复核） | 37 | 5.2% |
| 无候选（保持电商综合） | 2 | 0.3% |

结果固化为 `sql/03_backfill_pdd.sql`：**696 笔**写入具体品类，
「电商综合」1015 → 319 笔，需人工补品类的从 147 笔降到 58 笔。
回填顺带暴露了分类体系的缺口，新增 **食品生鲜 GROC**（294→315 笔 ¥3,843.90，
占拼多多消费 41%，`is_durable = 0` 不参与闲置建模）。

### 商品名补全（2026-10-14）

上面那一步解决了"这笔算什么品类"，但**没解决"这笔到底买的是什么"**。

问题的严重程度：标注候选 776 笔里有 653 笔是拼多多，其中 **523 笔的「商品说明」
是占位文本**（`先用后付` / `消费` / `/` / `订单标题`）。人工标注时看到
「¥12.80 先用后付」根本回忆不起买了什么 —— 这不是标注人记性差，是数据源没有这个信息。

三种做法都不行：

| 想法 | 为什么不行 |
|------|-----------|
| 直接改 `t_transaction.product_desc` | 它是 `dedup_key` 的输入，改了同一份账单重导会算出不同指纹 → 整批数据翻倍 |
| 把商品名塞进 `t_idle_label.note` | 标签表是**标注结果**，不是商品事实；且同一交易的商品名应该独立于标注存在 |
| 只留在 CSV 里 | 工作台读库生成，CSV 到不了页面，等于白干 |

于是新增派生表 **`t_goods_detail`**（与 `t_trans_feature` 同一思路：可重建的东西
不写进事实表），把商品名、店铺、规格、匹配强度落库，`v_idle_candidate` 左连接带出。

匹配用两份回填结果合并（`--csv` 靠前的优先）：

| 来源 | 口径 | 覆盖 | 高置信率 |
|------|------|------|---------|
| `pdd_match.csv` | 只用「先用后付」扣款 | 716 笔 | 94.6% |
| `pdd_match_all.csv` | 全部拼多多支出 | 991 笔 | 76.9% |

先用先占坑取高质量的部分，② 只补 ① 没覆盖的：最终 **865 笔**拿到真实商品标题、
**94 笔**匹配没定夺（金额相同跨类，写进 `alt_titles` 交人工挑）、31 笔确实无从还原。

效果（以商品名补全当时的工作台 346 行为分母）：**有商品名 260 行 / 候选待判 34 行 /
只剩 16 行是纯平台单**，而改造前是 523 行占位文本。

> ⚠ **`sql/05_goods_detail.sql` 不入库**（已 gitignore）。它含真实店铺名与商品标题，
> 属个人购物记录；且商品名只能从**拼多多订单导出**还原，那份导出本身也不在仓库里。
> clone 仓库的人拿不到商品名，是数据使然，不是设计缺陷 —— 其余环节（品类、口径、
> 抽样、加权）全部可复现。

### 食品改判：吃的东西不参与闲置建模（2026-10-14）

商品名补全之后，工作台里立刻冒出一类新噪声：**零食、生鲜、饮料、调味**。
这些是即时消耗品 —— 买回来当天就吃掉，不存在"闲置"，逐笔标注纯属浪费人工。
（分类表里 GROC 的 `is_durable = 0` 本来就是这个意思，只是拼多多这批货
先前落在「电商综合 ECOMM」，没吃到这条规则。）

`scripts/reclass_food_as_groc.py` 就是修这个：扫候选池，命中食品的改判 GROC，
视图是 `is_durable = 1`，这些行自动掉出，工作台不用再解释。

判定按可信度分档，**宁可漏，不可错**：

| 依据 | 可信度 | 处理 |
|------|--------|------|
| `goods_title`（唯一命中的真实商品名） | 可信 | 命中食品 → 改判 |
| `alt_titles`（同金额的**多个候选**，` / ` 拼接） | 不可信 | 拆开逐段判，**每段都是食品**才改判 |
| 候选里混着食品（如「耳机 / 小鱼干 / 龙眼」） | 判不了 | 保持待标，工作台标红「含食品 n/m」提示 |

第二行是踩出来的：只要有一段是食品就改判，会把
「适用OPPO入耳式耳机 / 憨豆熊小鱼干 / 泰国龙眼」这笔**耳机**当零食移出。
所以多候选必须"全部通过"。

排除词一律用**具体词**，不用 `笔 / 锅 / 碗 / 杯 / 瓶 / 苹果` 这类裸词 ——
实测裸词会把这些一起误伤：蜡笔**小新**、空气炸**锅**食材、**苹果**手机、
纯**银耳**扣（被当"银耳"）、华夫**格**裤（被当"华夫饼"）、**茶叶**枕头、
**水果**牙签、**车厘子**色指甲油。

结果：候选池 776 → **712 笔**（64 笔改判），GROC 315 → 379 笔；
资金口径不受影响（改的是分类，不是 `is_consumption`），
四项基准 3783 / 2516 / ¥83,094.45 / 镜像 54 **零回归**。

> ⚠ `sql/06_food_as_groc.sql` 同样不入库（UPDATE 注释里带真实商品标题）。
> 规则（词表）在脚本里，换一份账单重跑就能得到自己的 06。

### 服务改判：服务/充值不参与闲置建模（2026-10-14）

驾校报名、话费充值这类**服务**同样不存在"买回来闲置"——它们要么被消费掉，
要么没消费，没有"买回来放着"这回事。但规则分类器按「商户 + 关键词」猜，
把「远景驾校 ¥1,300」「中国广电 ¥520」落进了 STUDY / LIFE。

代价很具体：候选池里 18 笔 ≥¥100 的大额，有 6 笔（¥1,820）是这类服务。
用户逐笔盘点时，得先替自动分类擦屁股 —— 这是"逐笔盘点"最隐蔽的成本。

`scripts/reclass_service.py` 只认**明确的商户名**（驾校 / 运营商 / 影城 / 健身房…），
或「商品说明写着充值 + 没有真实商品名」；`goods_title` 有值一律不动。
结果：候选池 712 → **705 笔**，大额 24 → 18 笔。

> 这一条和食品改判共同构成 **L1 自动层**：能被规则排除的，绝不让人看一眼。
> 见下节。

### 浪费体检：把人工从「笔」压到「类」（2026-10-14）

**问题**：逐笔盘点表（334 行 × 5 个字段）本质是**给自己造训练集**的研究工具，
不是产品功能。它的隐含前提是"标注者愿意为每一笔回忆、填 5 个字段"——
换任何一个人来用都不成立，也就是**没有普适性**。

**先说清楚绕不开的东西**：「这件东西闲置了没」这个信息，**账单里一个字都没有**
（微信/支付宝只记到收单机构，对方=「拼多多平台商户」、商品说明=「先用后付」）。
它只存在于人的事后记忆里。所以任何方案都需要人的输入，问题只是**把输入的单位
从「笔」换成「类」**。

**三层漏斗**（`scripts/gen_waste_checkup.py` → 「浪费体检」页）：

| 层 | 谁回答 | 本批工作量 |
|----|--------|-----------|
| L1 规则硬排除 | 不用人 | 食品生鲜 / 服务充值，靠 `is_durable = 0` 自动掉出 |
| L2 品类级判断 | 6 次点击 | 6 个品类的整体闲置倾向（每类给 6 个**真实商品名**做锚点） |
| L3 单品级确认 | 18 次点击 | ≥¥100 的笔单独问，因为钱高度集中在这里（占候选池 61%） |

人工量：**24 次点击**（逐笔盘点是 705 × 5 ≈ 3,525 次输入）。
代价要讲清楚：品类内的差异被平均掉（同类里有的在用有的闲置，最后只落一个比例）。
换来的是**可迁移性**——换一份别人的账单，同样只需要回答这几个品类问题 +
确认他自己的大额笔。这才是能被复用的形态。

导出两类，**精度不同、分开标注**：大额笔写 `sample_stratum = 'big_item'`（逐笔确认），
品类级写 `'cat_prior'`（先验推算，固定种子 20261014 抽样赋标签）。
后者是估计值，不能当 ground truth 用。

### 闲置标注口径（2026-10-12 定稿）

哪些交易"可能有闲置"不再靠 SQL 里手写 code 排除，而是分类表上的
**`t_category.is_durable`** 字段：`1` = 耐用品（可能有闲置），`0` = 即时消耗/服务
（消费完成瞬间就被消耗掉，闲置率恒为 0）。所有统计统一写 `is_durable = 1`。

- 新增分类 **生活服务 SERVICE**：共享吹风机（¥0.60/次）、共享洗衣、校内便利店、
  智慧零售柜共 **141 笔 ¥527.90**。它们原本混在"生活日用"里，会**系统性稀释闲置率**。
- 标注候选全集收敛到视图 **`v_idle_candidate`**（品类回填 → 商品名补全 → 食品改判
  → 服务改判后 **705 笔 / ¥23,059.73**），口径只有这一处。
- 小额（<¥20）占实物金额 26%，逐笔标注不现实 → **分层抽样 + 事后加权**：
  `≥20 元` 全标，`0~5 / 5~10 / 10~20` 三层各随机抽 60 笔（种子 20261012，可复现），
  共 **334 笔**。抽样脚本 `scripts/gen_label_workbench.py` 同时产出盘点工作台；
  加权还原见 `v_stratum_weight` / `v_category_idle_rate_weighted`。
- 逐笔工作台是**研究工具**（造训练集）；面向"想知道自己浪费了多少"的场景用
  `scripts/gen_waste_checkup.py` 产出的**浪费体检页**（24 次点击出结论），见上节。

### 页面自检（生成后必跑）

两个页面都是"整个前端内嵌进单个 HTML"的形态，SQL / Python / JS 三处字段名只要有一处
对不上，**页面不会报错，只会悄悄算出错误结果**。真实事故：工作台的 SQL 查出来叫
`trans_id`、JS 通篇写 `r.id`，于是 `r.id` 恒为 `undefined`，334 行共用同一份 state，
用户改任意一行、触发一次 render，全表一起变成"已移出/已判定"，导出的 SQL 还是
`WHERE trans_id=undefined` —— 一句报错都没有。

现在每个页面配两道闸：

1. 生成期断言：键必须存在、类型正确、互不重复（工作台是 `id`）；
2. `scripts/selftest_*.js` 用 Node + 最小 DOM 打桩把内嵌脚本真跑一遍（不需要浏览器）：
   工作台断言"改一行只影响一行"，体检页断言"改一个品类只影响那一个品类"、
   且导出内容落在真实键上。

```bash
node scripts/selftest_workbench.js "闲置盘点工作台.html"   # 9 项
node scripts/selftest_checkup.js   "浪费体检.html"          # 26 项
```

**别信"能下载"**：内置预览面板是沙箱 iframe，没有 `allow-downloads`，
`a.download` 会被**静默拦掉**——不报错、无提示，用户只看到"点了没反应"。
所以导出通道不能只有下载一条：

| 通道 | 何时能用 | 兜底 |
|------|---------|------|
| `navigator.clipboard.writeText` | 安全上下文 + 有权限 | 返回 `"hook"`（异步，不确定成败） |
| `document.execCommand("copy")` | 老接口，绝大多数情况可用 | 返回 `"ok"` / `"fail"` |
| 弹窗手动全选复制 | **永远可用** | `"fail"` / `"hook"` 时自动弹出 |

配套的「体检结果导入」页（`scripts/gen_result_import.py`）就是**粘贴通道**：
把导出的内容粘进去 → 核对 → 生成可落库 JSON，整条链路不经过下载。

## 数据库

MySQL 8.0，库名 `spending_waste`，字符集 `utf8mb4`。共 **9 张表 + 8 个视图**。

| 表 | 作用 |
|----|------|
| `t_user` | 用户与月度预算 |
| `t_category` | 消费分类（树形自关联） |
| `t_category_rule` | 自动分类关键词规则（带 priority 冲突消解） |
| `t_import_batch` | 账单导入批次（file_md5 防重复导入） |
| `t_transaction` | 交易明细（核心事实表） |
| `t_trans_feature` | 购买情境特征（与事实表分离，可整表重算） |
| `t_idle_label` | 闲置标注（模型标签，项目最核心的数据资产） |
| `t_risk_record` | 购买预警记录（含事后回填，构成评估闭环） |
| `t_goods_detail` | 商品名补全（派生表，从订单列表还原；不改账单原文，见上节） |

视图：`v_monthly_summary` / `v_category_idle_rate` / `v_top_waste` / `v_training_set` /
`v_source_coverage` / `v_idle_candidate` / `v_stratum_weight` / `v_category_idle_rate_weighted`

统计口径统一收敛到视图，应用层不重复写 WHERE 条件，避免同一指标多处算出不同结果。

### 四个关键设计（答辩时的加分点）

**1. 跨源重复必须处理，否则支出虚高。**
同一笔钱会在多处留痕：微信零钱通充值在工行记为「理财」，支付宝扫码付款在工行记为「消费」。
实测六份账单直接相加为 ¥103,704.43，剔除镜像行后为 ¥83,094.45 —— 其中 **¥20,609.98（19.9%）是重复计账**。
`t_transaction.is_primary` 标记镜像行，四个视图统一按 `is_primary = 1` 统计。
被剔的 54 笔构成：理财 7 笔 ¥13,584.08 / 缴费 2 笔 ¥5,519.68 / 消费 43 笔 ¥1,423.32 / 充值 1 笔 ¥62.90 / 转账 1 笔 ¥20.00。

**2. 去重不用平台订单号，用行指纹。**
订单号有缺失（银行流水根本没有）、格式互不相通、支付宝的还带制表符。
改用 `MD5(来源+时间+金额+对方+商品说明)`；订单号仅在存在时追加。
实测教训：微信有两笔「中铁网络 ¥279.50」时间精确到秒完全相同、对方与商品名也完全一致，
仅订单号不同 —— 只用五字段会丢数据。

**3. 分类分两层：方向层 + 关键词层。**
收入 / 资金调拨是**事实**，账单里已经标了 `direction`，不该用关键词去猜。
第一版只用关键词，导致 103 笔真实支出（商品名写作「收款方备注:二维码收款」）
被误判成"收入"。现在按 `direction` 先判，关键词只用于"支出"的品类细分。

**4. 事实表只放事实，能重算/能补全的东西另立派生表。**
`dedup_key = MD5(来源+时间+金额+对方+商品说明)`，所以 `product_desc` 是**指纹的输入**，
一旦就地覆盖商品名，同一份账单重导会算出不同指纹、整批数据翻倍。
故商品名补全走 `t_goods_detail`、情境特征走 `t_trans_feature`：两者都能整表重建，
事实表保持只读。这条规则救了两次场（改特征、补商品名）。

### 事故复盘：脚本写死 category_id，把主库删了

为建一个临时导入库，我用 `sed` 批量改 `<库名>` 重跑 `sql/01_schema.sql`，
但**只替换了 `CREATE DATABASE`，漏掉第 15 行的 `DROP DATABASE IF EXISTS spending_waste`**
——脚本自己把主库删了。恢复链（**已实测可用，写在这里当 SOP**）：

```bash
# 1. 重建空库（备份是 --no-create-db 导出的，不含 CREATE/USE，必须先建库）
mysql -uroot -e "CREATE DATABASE spending_waste DEFAULT CHARSET utf8mb4"
# 2. 灌回备份（884K，含 3783 行）
mysql -uroot spending_waste < "F:/allstudy/_db_backup/spending_waste_20261014_回填拼多多品类前.sql"
# 3. 幂等重放脚本链（全部 + 子查询写法，可反复跑）
mysql -uroot spending_waste < sql/03_backfill_pdd.sql   # 候选池 1114→776
mysql -uroot spending_waste < sql/04_add_goods_detail.sql
mysql -uroot spending_waste < sql/05_goods_detail.sql   # 959 行
mysql -uroot spending_waste < sql/06_food_as_groc.sql   # 776→712
mysql -uroot spending_waste < sql/07_service_out.sql    # 712→705
```

重放后逐项校验：**3783 / 2516 / ¥83,094.45 / 资金镜像 54**，候选池 **705**，
品类分布 ECOMM 256 / APPAREL 155 / LIFE 151 / STUDY 110 / DIGITAL 17 / HOBBY 16
—— 与事故前完全一致，零数据损失。

两条硬教训：

1. **`category_id` 不可写死。** `AUTO_INCREMENT` 在恢复后从 1 重排，
   原先 `GROC = 14`、恢复后变成 **94**。写死 14 会直接踩
   `ERROR 1452 (23000): Cannot add or update a child row ... fk_trans_category`。
   所有补丁脚本一律写
   `SET category_id = (SELECT category_id FROM t_category WHERE category_code='GROC')`。
2. **临时库用完立刻 drop。** 事故的诱因就是 `spending_waste_import` 这个临时库
   长期留在实例里，才需要去改 `01_schema.sql`。现在实例里只有
   `spending_waste / sqlpractice / school` 三个业务库。
